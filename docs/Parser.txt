Parser (Синтаксический анализатор)

Назначение:
Parser преобразует последовательность токенов, полученную от лексера (Lexer),
в структуру Statement — промежуточное представление SQL-запроса, пригодное
для исполнения ядром СУБД. Основная цель класса — проверить корректность
порядка токенов согласно упрощённой грамматике команд INSERT и SELECT,
а в случае обнаружения синтаксической ошибки — предоставить информативное
описание проблемы. Код устойчив к выходу за пределы массива токенов и
поддерживает регистронезависимые ключевые слова.

Основные структуры:
- StatementType — перечисление возможных типов операторов: INSERT, SELECT, UNKNOWN.
- Statement — базовая структура, представляющая распознанную команду. Содержит:
  - type (StatementType) — тип операции,
  - insert_id (uint32_t) — числовой идентификатор для INSERT,
  - insert_text (std::string) — строковое значение для INSERT,
  - select_all (bool) — флаг "SELECT *" (true означает SELECT * FROM table).

Логика работы:

1. Инициализация
Парсер получает вектор токенов от лексера и устанавливает внутренний указатель
pos_ на начало. Токены хранятся в поле tokens_.

2. Основной цикл parse()
- Проверяется, не пуст ли поток токенов. Если токенов нет, выбрасывается
  std::invalid_argument с сообщением «Пустой запрос».
- Считывается первый токен (peek()). Он обязан быть ключевым словом (KEYWORD).
  Если это не так, выбрасывается исключение с указанием, что ожидалось ключевое
  слово INSERT или SELECT.
- Значение ключевого слова приводится к верхнему регистру (функция to_upper)
  для регистронезависимого сравнения. В зависимости от команды вызывается
  parse_insert() или parse_select().
- После разбора основной команды проверяется наличие завершающего символа ';'.
  Если следующий токен — SYMBOL со значением ";", он поглощается. Если это
  не конец файла и не ';', выбрасывается исключение. Таким образом, запрос
  "INSERT 1 'text'" будет разобран успешно, а "INSERT 1 'text' something" — нет.

3. Разбор INSERT — метод parse_insert()
Ожидается строгая последовательность токенов:
   [KEYWORD "INSERT"] (уже поглощён перед вызовом) → NUMBER → STRING.
- Вызывается consume() для пропуска токена INSERT.
- Проверяется наличие токена. Если достигнут конец, выбрасывается ошибка
  с текстом «ожидался идентификатор (число)».
- Следующий токен должен быть NUMBER. Если тип не совпадает, исключение
  содержит полученное значение.
- Числовое значение преобразуется в unsigned long через std::stoul и
  проверяется на принадлежность диапазону uint32_t (≤ 4294967295). При
  превышении выбрасывается исключение «число слишком большое». Также
  перехватываются исключения от std::stoul при неверном формате числа.
- Аналогично проверяется и извлекается строковый токен STRING. При отсутствии
  или неверном типе генерируется ошибка «ожидалась строка».
- По успешному извлечению заполняется Statement: type = INSERT, insert_id и
  insert_text устанавливаются из токенов.

4. Разбор SELECT — метод parse_select()
Ожидается последовательность:
   [KEYWORD "SELECT"] → SYMBOL "*" → IDENTIFIER "FROM" → IDENTIFIER (имя таблицы).
- Пропускается токен SELECT.
- Проверяется наличие '*'. Токен должен иметь тип SYMBOL и значение "*". Иначе
  ошибка.
- Далее ожидается ключевое слово FROM. Поскольку текущая версия лексера не
  классифицирует FROM как отдельное ключевое слово, парсер принимает его как
  IDENTIFIER со значением "FROM" (с приведением к верхнему регистру).
- Последний обязательный токен — имя таблицы (тип IDENTIFIER). При отсутствии
  или ином типе выбрасывается исключение.
- Формируется Statement с type = SELECT и select_all = true. Имя таблицы
  временно не сохраняется (структура Statement может быть расширена позже).

5. Служебные методы для работы с токенами
- consume() — возвращает текущий токен и сдвигает указатель. Если достигнут
  конец потока, выбрасывается исключение.
- peek() — возвращает текущий токен без сдвига. Используется для предварительной
  проверки типа/значения.
- is_at_end() — возвращает true, если указатель вышел за границы вектора или
  текущий токен имеет тип END_OF_FILE. Это гарантирует, что ни один метод
  не попытается обратиться к несуществующему элементу.

6. Обработка ошибок и защита
Все методы, читающие токены, предварительно проверяют is_at_end(). При попытке
доступа за концом немедленно выбрасывается std::invalid_argument с описанием,
позволяющим быстро локализовать проблему (например, «Синтаксическая ошибка в
INSERT: ожидалась строка»). Это делает парсер устойчивым к неполным или
некорректным последовательностям токенов, предотвращая аварийное завершение.
Дополнительно в INSERT проверяется, что числовой идентификатор не выходит за
пределы 32-битного беззнакового целого, что исключает скрытое переполнение при
приведении типов.

Взаимодействие с другими модулями:
- Lexer — поставляет подготовленный вектор токенов. Парсер не зависит от
  исходного текста запроса, работая исключительно с типами и значениями токенов.
  Приведение ключевых слов к верхнему регистру позволяет корректно обрабатывать
  слова, сохранённые лексером в исходном регистре. Из-за того, что лексер пока
  распознаёт как ключевые слова только INSERT и SELECT, парсер обрабатывает
  FROM как идентификатор с ожидаемым значением.
- Ядро СУБД (будущий модуль исполнения) — получает от парсера структуру Statement
  и на основе её полей выполняет соответствующую операцию (вставка или выборка).
- Система обработки ошибок — все исключения наследуются от std::invalid_argument,
  что позволяет верхнему уровню (REPL) перехватывать их и выводить пользователю
  информативное сообщение без раскрытия деталей реализации.

Особенности реализации, важные для защиты:
- Регистронезависимость ключевых слов. Лексер может вернуть слова в том виде,
  в котором их ввёл пользователь (insert, Insert, INSERT). С помощью to_upper
  они приводятся к единому регистру, что делает парсер более удобным для
  конечного пользователя и соответствует требованию «смешение регистров в одном
  слове не допускается». Сравнение с "FROM" также регистронезависимо.
- Проверка завершающей точки с запятой. Хотя текущая упрощённая грамматика
  допускает её отсутствие, парсер всё же проверяет, что после основной команды
  нет лишних токенов, кроме необязательного ';'. Это предотвращает исполнение
  запросов с мусорными суффиксами.
- Контроль диапазона чисел. При разборе INSERT значение ID проверяется на
  принадлежность uint32_t, чтобы избежать неопределённого поведения из-за
  переполнения и гарантировать корректное сохранение в 32-битном поле.
- Чёткое разделение ответственности: Parser не занимается лексическим анализом,
  а только синтаксическим контролем и формированием структуры Statement. Это
  позволяет в будущем легко расширить грамматику, добавив новые методы parse_
  без изменения уже существующих.
- Адаптация к ограничениям лексера. Так как лексер на данном этапе не выделяет
  FROM как ключевое слово, парсер корректно обрабатывает его как идентификатор,
  что демонстрирует устойчивость к изменениям в лексере и готовность к
  дальнейшей доработке лексического анализа.
- Простота расширения. Структура Statement может быть дополнена полями для
  более сложных запросов (WHERE, JOIN и т.д.), сохраняя обратную совместимость
  для уже реализованных команд.
